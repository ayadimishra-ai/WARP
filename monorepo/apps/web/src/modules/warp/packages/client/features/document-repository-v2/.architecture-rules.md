# Document Repository V2 - Architecture Rules

**Quick Reference**: When adding a feature, ask "Where does this belong?"

- **Pure logic? → Domain layer** (document.rules.ts, document.selectors.ts)
- **Data fetching? → Server layer** (fetchDocuments.ts - SSR compatible)
- **State/Effects? → Application layer** (use\*.ts hooks)
- **Display? → UI layer** (\*.tsx components)
- **Wiring? → Page layer** (document-repository.tsx - composition only)

## Core Principles

### 1. **Event-Driven, Not Effect-Driven**

- **NEVER** use `useEffect` for data fetching in page layer
- Use explicit event handlers: `onClick`, `onDrop`, `onSubmit`
- SSR fetching via `getServerSideProps` in parent page
- Client-side refetching via application layer hooks (useDocuments)

### 2. **Strict Layer Separation**

```
domain/           → Pure TypeScript (types, rules, selectors)
server/           → SSR-compatible data fetching (GraphQL queries)
application/      → React hooks for state orchestration
ui/               → Pure UI components (memoized, props-only)
pages/            → Composition ONLY (hook calls + JSX)
```

### 3. **Page Layer Rules**

**ALLOWED in pages/document-repository.tsx:**

- Import and call application hooks
- Import and render UI components
- Define event handlers using `useCallback`
- Derive display data using `useMemo`
- Receive props from parent Next.js page

**FORBIDDEN in pages/document-repository.tsx:**

- `useEffect` for data fetching
- `useState` for business data (templates, documents, subscription)
- Direct Apollo Client calls (`apolloClient.query()`)
- Business logic (validation, calculations)
- GraphQL query/mutation execution
- Direct API calls

### 4. **Data Flow Pattern**

```typescript
// CORRECT: SSR in parent page
// apps/web/pages/document-repository.tsx
export async function getServerSideProps(context) {
  const session = await embeddedAuthGuard(context);
  const apolloClient = initializeApollo();

  // Fetch ALL initial data server-side
  const templates = await fetchDocumentTemplates();
  const documents = await fetchDocuments(userContext);
  const subscription = await fetchSubscriptionStatus(userContext);

  return {
    props: {
      initialDocuments: documents,
      templates,
      subscription,
      userContext
    }
  };
}

// CORRECT: Composition in v2 page
// features/document-repository-v2/pages/document-repository.tsx
export default function DocumentRepositoryPage({
  initialDocuments,
  templates,    // ← Always provided via SSR
  subscription, // ← Always provided via SSR
  userContext
}) {
  // Only hook composition and event handlers
  const { documents, refreshDocuments } = useDocuments({ initialDocuments, userContext });
  const { uploadFiles } = useUploadManager({ userContext, onUploadComplete: ... });

  return <DocumentGrid ... />;
}
```

```typescript
//WRONG: Client-side fetching in page
export default function DocumentRepositoryPage({ ... }) {
  const [templates, setTemplates] = useState([]);

  useEffect(() => {
    //NEVER do this in page layer!
    fetchDocumentTemplates().then(setTemplates);
  }, []);
}
```

### 5. **State Management Rules**

**Application Layer (hooks):**

- Encapsulate `useState` for specific concerns
- Handle side effects internally (mutations, polling)
- Expose event handlers, not setters
- Return derived state and actions

**Page Layer:**

- NO `useState` for business data
- ONLY `useMemo` for display transformations
- ONLY `useCallback` for event handler memoization

### 6. **When You Think "I Need useEffect in Page"**

**STOP and ask:**

1. Should this be SSR? → Add to parent's `getServerSideProps`
2. Should this be in a hook? → Create/extend application layer hook
3. Is this polling? → Use `usePolling` hook
4. Is this a side effect of user action? → Make it an event handler

**Example Refactors:**

```typescript
//WRONG: Effect in page
useEffect(() => {
  if (templates.length === 0) {
    fetchTemplates().then(setTemplates);
  }
}, [templates]);

//CORRECT: SSR in parent
// apps/web/pages/document-repository.tsx
const templates = await fetchDocumentTemplates();

//ALTERNATIVE: Application hook
// application/useTemplates.ts
export function useTemplates(userContext) {
  const [templates, setTemplates] = useState([]);
  // ... internal effect logic
  return { templates };
}
```

### 7. **GraphQL Usage**

- Import from `@/modules/warp/packages/graphql/queries/generated/[name]`
- Use `[QueryName]Document` export
- Execute in server layer or application hooks
- NEVER execute queries directly in page layer

### 8. **Error Handling**

```typescript
//WRONG: Try-catch in page
const handleUpload = async () => {
  try {
    await uploadFiles(...);
  } catch (error) {
    setError(error);
  }
};

//CORRECT: Error handling in hook
// application/useUploadManager.ts
export function useUploadManager({ onUploadError }) {
  const uploadFiles = async (...) => {
    try {
      // ... upload logic
    } catch (error) {
      onUploadError(error, fileName); // ← Hook handles error
    }
  };
  return { uploadFiles };
}

// Page just provides error callback
const { uploadFiles } = useUploadManager({
  onUploadError: (error, fileName) => {
    showToast(`Upload failed: ${fileName}`);
  }
});
```

### 9. **Testing Implications**

**Because pages are composition-only:**

- Test hooks independently with React Testing Library
- Test UI components with Storybook
- Test business logic with pure function tests
- Page becomes integration test only

### 10. **Migration Checklist**

When writing new code, verify:

- [ ] Page layer has ZERO `useEffect`
- [ ] Page layer has ZERO `useState` for business data
- [ ] All data fetching is SSR or in hooks
- [ ] All event handlers use `useCallback`
- [ ] All derived data uses `useMemo`
- [ ] No business logic in page
- [ ] No direct GraphQL calls in page

## Common Mistakes to Avoid

### Mistake 1: "Templates are empty, let me fetch them"

```typescript
//WRONG
if (templates.length === 0) {
  useEffect(() => fetchTemplates(), []);
}

//CORRECT - Fix the root cause
// Parent page wasn't fetching in getServerSideProps
```

### Mistake 2: "I need loading state"

```typescript
//WRONG - Adding loading state in page
const [isLoading, setIsLoading] = useState(false);

//CORRECT - Hook manages loading
const { documents, isLoading } = useDocuments(...);
```

### Mistake 3: "Quick polling with useEffect"

```typescript
//WRONG
useEffect(() => {
  const interval = setInterval(refresh, 5000);
  return () => clearInterval(interval);
}, []);

//CORRECT
usePolling({ enabled: true, interval: 5000, onPoll: refresh });
```

## File-Specific Rules

### `pages/document-repository.tsx`

- **Lines of code:** ~200-250 (composition + event handlers)
- **Max complexity:** If > 250 lines, extract to sub-components
- **Imports:** Only from `../application`, `../ui`, `../domain` (selectors/types)
- **No imports from:** `@apollo/client` (except types), server layer, GraphQL generated

### `application/*.ts` hooks

- **One concern per hook:** Don't create mega-hooks
- **Return shape:** `{ data, actions, status }` pattern
- **Internal effects:** Use `useEffect` internally as needed
- **External API:** Only expose event handlers

### `server/*.ts`

- **No React:** Pure async functions
- **SSR compatible:** No browser APIs
- **Error handling:** Always catch and transform errors
- **Return types:** Always return domain types

### Pattern: Auto-Navigation After State Change

**Problem**: Navigate to main view when last expired document deleted

**Anti-Pattern**: Using useState to track navigation intent

```typescript
// ❌ WRONG - State in page layer
const [shouldNavigate, setShouldNavigate] = useState(false);
useEffect(() => {
  if (shouldNavigate && expiredCount === 0) {
    setShowExpiredOnly(false);
  }
}, [shouldNavigate, expiredCount]);
```

**Correct Pattern**: Calculate directly from returned fresh data

```typescript
// ✅ CORRECT - No state, pure calculation
const handleDeleteComplete = async () => {
  const freshDocuments = await refreshDocuments(); // Returns Promise<Document[]>
  const freshExpiredCount = countExpiredDocuments(freshDocuments);

  if (showExpiredOnly && freshExpiredCount === 0) {
    setShowExpiredOnly(false);
  }
};
```

### Pattern: Bifurcated Views with Correct Counts

**Problem**: Main view button shows total count, but expired docs are in separate tab

**Solution**: Calculate non-expired count separately

```typescript
// Domain: Use inverse of expired filter
const mainViewCount = useMemo(() => {
  const expiredTemplates = getTemplatesWithExpiredDocuments(documents, expandedTemplates);
  const expiredTemplateIds = new Set(expiredTemplates.map(t => t.id));
  return expandedTemplates.filter(t => !expiredTemplateIds.has(t.id)).length;
}, [documents, expandedTemplates]);

// UI: Pass both counts
<DocumentGrid
  expiredCount={expiredCount}      // For expired tab
  mainViewCount={mainViewCount}    // For main view
/>
```

### Pattern: Newest-First Sequencing for Dynamic Lists

**Problem**: New "Other" uploads appearing at end instead of top

**Solution**: Reverse sort order in domain selector

```typescript
// OLD: Oldest first (a < b)
sortedOtherDocuments.sort(
  (a, b) => new Date(a.createdAt).getTime() - new Date(b.createdAt).getTime()
);

// NEW: Newest first (b < a)
sortedOtherDocuments.sort(
  (b, a) => new Date(b.createdAt).getTime() - new Date(a.createdAt).getTime()
);
```

### Pattern: Expiry Status Distinction

**Problem**: "Expired" tab showing both expired AND expiring soon documents

**Solution**: Use `isDocumentExpired` (strict) vs `isDocumentExpiring` (lenient)

```typescript
// Domain: Two distinct functions
export function isDocumentExpiring(doc: Document): boolean {
  const status = calculateExpiryStatus(doc.expiryDate);
  return (
    status === ExpiryStatus.Expired || status === ExpiryStatus.ExpiringSoon
  );
}

export function isDocumentExpired(doc: Document): boolean {
  const status = calculateExpiryStatus(doc.expiryDate);
  return status === ExpiryStatus.Expired; // Strict - only past expiry
}

// Usage:
if (filters.showExpiredOnly) {
  filtered = filtered.filter(isDocumentExpired); // Strict for expired tab
} else {
  filtered = filtered.filter((doc) => !isDocumentExpired(doc)); // Allow "expiring soon" in main view
}
```

## Summary

**The Golden Rule:**

> If you're writing `useEffect`, `useState`, or Apollo Client code in the page layer, YOU'RE DOING IT WRONG. Move it to the appropriate layer.

**When in doubt:**

1. Business logic → domain layer
2. Data fetching → server layer (SSR) or application hooks (client)
3. State management → application hooks
4. User interaction → page event handlers
5. Display → UI components
6. Auto-navigation → Calculate from returned values, not effects
7. Filtering → Domain selectors with clear semantics (strict vs lenient)
8. Counts → Derived from filtered data, not separate state
